## 読むもの
- `soujo`（PATH 上のコマンド）・git・`.soujo/` は作業中のプロジェクトのもの。スキルの置き場所へ cd したり、そこの `.soujo/`・`dist/` を使ったりしない。コマンドはツール呼び出し1回に1つだけ実行し、`&&`・`;` でつながない（許可リストに拒まれることがある）。`soujo` が見つからなければ止めて1行で伝える。
- `soujo init` の後の `.soujo/SPEC.md`。埋まっている節は聞き直さない（見出しのない節は足す）。
- 技術の候補を出すときはリポジトリの設定ファイル（`package.json`・`go.mod`・`mix.exs` など）、原則の候補を出すときはそれとリポジトリが文書で述べる慣習（README・CONTRIBUTING など）だけ。

## やること
- 1メッセージに1問。答えを受けてから次の問いへ（質問ツールでも1回1問）。最大7問、各問に番号付きの答え候補を付ける。原則は1問で決め、候補はそれまでの答え・設定ファイル・述べられた慣習から出す（複数選んでよい）。
- 答えを得るたびに、次の問いを出す前に該当節（原則・目的・やらないこと・受け入れ基準・技術判断）へ書く（中断しても答えが SPEC.md に残る。まとめて最後に書かない）。原則は `- P<n> <名前> — <判定できる1文>` で7行まで、受け入れ基準の字下げのない項目は `- A<n> <判定できる1文>`。キーは再利用も振り直しもせず、既存の SPEC のキーのない原則・基準は、意味を変えずにこの形へ直す（原則には名前と `—` も補う）。技術スタックは設定ファイルで決まっていればそれを書き、決まらなければ聞く（既定値を持たない）。
- 5節が埋まるか7問に達したら終える。埋まらない節は「未定」と書く。ただし原則が決まらなければ、原則の節は「未定」と書かず空のままにする。100行以内。`次:` が PLAN の未完了の層なら next set はしない。

## soujo に頼むこと
- 最初に `soujo init`（`.soujo/` と、無ければ CLAUDE.md / AGENTS.md を作る。既存は上書きしない）。git リポジトリでないと出たら、`git init` するかを1問目で聞く。
- 書き終えたら節目を残す：`soujo log add '節目' --line 'SPEC.md を書いた: <目的の要点>（原則を変えたら 原則: <変えたキーと何を>）' --line '未決: <「未定」の節と、決まらず空のままの原則。なければ なし>'`（1行目は `soujo brief` に出る。後のコマンドが失敗しても繰り返さない）。
- 続けて `soujo next set --layer 'plan' --premise 'SPEC.md 完成' --check 'PLAN.md に層と完了条件が並ぶ'`（plan の effort は CLI が high にするので `--effort` は付けない）。

## 出力の形
- 質問中は、1問と番号付きの候補の短い表だけ。
- 終わりに `SPEC.md` の骨組みの表1つ（節 / 要点。原則はキーと名前）と、`soujo init` が作ったファイルの1行。
